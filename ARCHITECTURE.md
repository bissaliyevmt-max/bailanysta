# Разбор архитектуры

Документ для того, чтобы разобраться в проекте и суметь объяснить любую
его часть. README рассказывает **что** сделано — здесь **почему так**
и **как это работает**.

---

## 1. Общая картина

Приложение состоит из четырёх слоёв. Каждый знает только про соседний снизу:

```
┌─────────────────────────────────────────────────────┐
│  Браузер: React-компоненты                          │
│  src/components/**, src/app/**/page.tsx             │
│  Знают: какие есть эндпоинты. Не знают: про базу.   │
└──────────────────────┬──────────────────────────────┘
                       │  fetch('/api/...')
┌──────────────────────▼──────────────────────────────┐
│  Сервер: API-эндпоинты                              │
│  src/app/api/**/route.ts                            │
│  Разобрать запрос → вызвать функцию → вернуть JSON  │
└──────────────────────┬──────────────────────────────┘
                       │  вызов функции
┌──────────────────────▼──────────────────────────────┐
│  Слой данных и бизнес-правил                        │
│  src/lib/queries.ts                                 │
│  Единственное место, где пишутся запросы к базе     │
└──────────────────────┬──────────────────────────────┘
                       │  Drizzle ORM → SQL
┌──────────────────────▼──────────────────────────────┐
│  PostgreSQL                                         │
│  Схема: src/db/schema.ts                            │
└─────────────────────────────────────────────────────┘
```

**Зачем такое разделение.** Если завтра понадобится мобильное приложение,
оно подключится к тем же эндпоинтам. Если поменяется база — правится только
`queries.ts`. Если бы компоненты ходили в базу напрямую, любое изменение
задевало бы весь проект.

**Что где физически выполняется.** Файлы в `src/app/api/` и всё, что они
импортируют, выполняются на сервере. Файлы с директивой `'use client'`
в первой строке — в браузере. Это и есть граница, за которую не должен
уходить ключ OpenAI.

## 2. Проход одного действия насквозь

Разберём постановку лайка — в ней участвуют все слои.

**Шаг 1. Клик.** `src/components/PostCard.tsx`, функция `toggleLike`.
Первым делом интерфейс обновляется, не дожидаясь сервера:

```ts
const optimistic = {
  ...post,
  likedByViewer: !post.likedByViewer,
  likeCount: post.likeCount + (post.likedByViewer ? -1 : 1),
};
onChanged(optimistic);   // сердечко закрасилось мгновенно
```

Это называется **оптимистичным обновлением**: мы предполагаем, что запрос
пройдёт успешно. Если он упадёт — вернём как было.

**Шаг 2. Запрос.** `api.post('/api/posts/12/like')` из `src/lib/client.ts`.
Обёртка добавляет заголовки и превращает `{ error: "..." }` в исключение.

**Шаг 3. Эндпоинт.** `src/app/api/posts/[id]/like/route.ts`:

```ts
const me = await requireCurrentUser();       // кто это делает
const result = await toggleLike({ postId: Number(id), viewerId: me.id });
return ok(result);
```

Три строки. Вся логика — на следующем уровне.

**Шаг 4. Бизнес-правила.** `toggleLike` в `src/lib/queries.ts`:

1. Проверяет, что пост существует, иначе `notFound(...)` → `404`.
2. Смотрит, есть ли уже лайк этого пользователя.
3. Есть — удаляет. Нет — вставляет **и создаёт уведомление автору**,
   но только если автор — не сам лайкающий.
4. Пересчитывает количество лайков одним SQL-запросом `count(*)`.

Именно здесь живёт правило «не уведомлять самого себя». Если бы оно было
в эндпоинте, его пришлось бы дублировать при каждом новом способе
поставить лайк.

**Шаг 5. Возврат.** Компонент получает настоящие числа и заменяет ими
оптимистичные. При ошибке — `onChanged(post)` возвращает исходное состояние.

## 3. База данных

Шесть таблиц (`src/db/schema.ts`):

```
users ──┬─< posts ──┬─< likes
        │            ├─< comments
        │            └─< notifications
        ├─< follows (follower_id → users, following_id → users)
        └─< notifications (user_id — получатель, actor_id — кто сделал)
```

### Что стоит уметь объяснить

**Почему у `likes` составной первичный ключ, а не обычный `id`.**

```ts
primaryKey({ columns: [table.postId, table.userId] })
```

Это означает: пара «пост + пользователь» может существовать только в одном
экземпляре. Двойной клик или два одновременных запроса не создадут два лайка —
второй просто не вставится. Проверка в коде (`если лайка нет, то вставить`)
такой гарантии не даёт: между проверкой и вставкой проходит время, и за него
может пройти второй запрос. Это классическая гонка, и решается она
ограничением в базе, а не в приложении.

То же самое у `follows`: нельзя подписаться на одного человека дважды.

**Что такое `onDelete: 'cascade'`.** Указано у внешних ключей. Удаляем пост —
его лайки, комментарии и уведомления удаляются автоматически, силами базы.
Без этого пришлось бы удалять их вручную в четыре запроса, и любой
пропущенный оставил бы «мусор», ссылающийся в пустоту.

**Почему хэштеги — отдельная колонка-массив.** Можно было искать регуляркой
по тексту поста. Но тогда поиск `#fin` находил бы `#finance`, а каждый
поисковый запрос заставлял бы базу читать все посты целиком. Массив
заполняется один раз при сохранении, а поиск делает оператор Postgres `&&`
(«массивы пересекаются») — точно и быстро.

**Зачем индексы.** `posts_created_at_idx` — лента всегда сортируется по дате.
Без индекса база на каждый запрос сортировала бы всю таблицу целиком.
На восьми постах разницы нет, на ста тысячах — это разница между 5 мс и 2 с.

**Подсчёт лайков подзапросом.** В `queries.ts`:

```sql
(select count(*)::int from likes where likes.post_id = posts.id)
```

Альтернатива — вытащить все лайки в Node и посчитать там. Это привело бы
к **проблеме N+1**: один запрос за постами плюс по одному запросу за лайками
каждого поста. Двадцать постов — двадцать один запрос вместо одного.

## 4. Кто такой «текущий пользователь»

Полноценной авторизации нет (см. README, раздел «компромиссы»). Вместо неё:

1. В cookie `bailanysta_uid` лежит id пользователя.
2. Cookie помечена `httpOnly` — JavaScript в браузере её не прочитает
   и не подменит.
3. `getCurrentUser()` в `src/lib/session.ts` читает её на сервере
   и достаёт пользователя из базы.
4. Если cookie нет (первый заход) — берётся первый пользователь из базы,
   чтобы приложение сразу было живым.

Переключатель пользователя (`PUT /api/me`) просто перезаписывает cookie.

**Важно для защиты:** проверка прав («это ваш пост?») делается на сервере,
в `queries.ts`, а не в интерфейсе. Кнопки «Изменить» и «Удалить» в UI скрыты
у чужих постов, но если отправить `PATCH` напрямую через `curl`, сервер
вернёт `403`. Скрытая кнопка — это удобство, а не защита.

## 5. Как устроена тёмная тема

Три части работают вместе:

**1. Класс на `<html>`.** Tailwind v4 настроен так, что `dark:`-классы
срабатывают, когда на корневом элементе есть класс `.dark`
(`@custom-variant dark` в `globals.css`).

**2. Синхронный скрипт в `<head>`** (`themeInitScript` в `ThemeProvider.tsx`).
Он выполняется **до первой отрисовки страницы**: читает `localStorage`
и вешает класс. Если бы это делалось в `useEffect`, браузер успел бы
показать светлую страницу — и пользователь в тёмной теме видел бы белую
вспышку при каждой загрузке. Это частая ошибка, и её стоит уметь назвать.

**3. React-контекст** подхватывает уже выставленное значение и умеет его
переключать, записывая выбор в `localStorage`.

Запись в `localStorage` обёрнута в `try/catch`: в приватном режиме браузера
она может быть запрещена, и падать из-за этого приложение не должно.

## 6. Как устроена AI-генерация

Это самое проверяемое место по ТЗ: «все внешние сервисы вызываются
с серверной части».

```
Браузер                    Наш сервер                  OpenAI
   │                           │                          │
   │ POST /api/ai/generate     │                          │
   │ { topic: "..." }          │                          │
   ├──────────────────────────>│                          │
   │                           │ читает OPENAI_API_KEY    │
   │                           │ из process.env           │
   │                           ├─────────────────────────>│
   │                           │<─────────────────────────┤
   │<──────────────────────────┤                          │
   │ { content, source }       │                          │
```

**Три уровня защиты ключа:**

1. Переменная называется `OPENAI_API_KEY`, а не `NEXT_PUBLIC_OPENAI_API_KEY`.
   Next.js кладёт в браузерный бандл только переменные с префиксом
   `NEXT_PUBLIC_` — остальные физически недоступны клиенту.
2. `src/lib/ai.ts` помечен директивой `import 'server-only'`. Попытка
   импортировать его в клиентский компонент **уронит сборку**.
3. Проверяемо командой: `grep -r "OPENAI_API_KEY" .next/static/` — пусто.

**Запасной вариант.** Если ключа нет или OpenAI недоступен, включается
встроенный генератор (`offlineDraft`), и в ответе приходит `note`
с объяснением. Приложение не падает из-за чужого сервиса — это разница
между демо и рабочим продуктом.

**Таймаут.** Запрос к OpenAI обёрнут в `AbortController` с лимитом 20 секунд.
Без него зависший внешний сервис заблокировал бы серверную функцию.

## 7. Почему ошибки возвращают разные коды

`src/lib/errors.ts` вводит класс `AppError`, который несёт HTTP-статус:

```ts
throw badRequest('Текст поста не может быть пустым');   // 400
throw forbidden('Можно редактировать только свои посты'); // 403
throw notFound('Пост не найден');                         // 404
```

Обработчик `handle()` в `src/lib/http.ts` различает их:

```ts
if (error instanceof AppError) return fail(error.message, error.status);
console.error('[api]', error);              // настоящая поломка — в лог
return fail(message, 500);
```

Без этого пустой пост возвращал бы `500`, как будто сервер упал. Разница
принципиальная: `4xx` — «вы прислали что-то не то», `5xx` — «у нас сломалось».
Мониторинг, ретраи и алерты строятся именно на этом различии.

## 8. Почему часть компонентов клиентские, а часть серверные

Next.js App Router по умолчанию делает компоненты **серверными**: они
выполняются на сервере, в браузер уходит готовый HTML, их код не попадает
в бандл.

Директива `'use client'` в первой строке делает компонент **клиентским**.
Она нужна там, где есть интерактивность: `useState`, `useEffect`,
обработчики событий, доступ к `localStorage`.

В проекте:

- **Серверные:** `src/app/page.tsx`, `src/app/u/[username]/page.tsx`,
  `layout.tsx`. Они читают параметры адреса и передают их вниз.
- **Клиентские:** всё в `src/components/` — там клики, состояние и запросы.

Граница проходит по принципу «как можно ниже»: чем меньше клиентских
компонентов, тем меньше JavaScript уезжает в браузер.

**Параметры в Next.js 16 асинхронные.** И `params`, и `searchParams` —
это `Promise`, их нужно `await`. Частая ошибка при переходе со старых
версий.

## 9. Что бы делалось дальше

Если бы проект развивался, следующие шаги в порядке приоритета:

1. **Настоящая аутентификация** — NextAuth или Clerk. Слой сессии уже
   изолирован в `src/lib/session.ts`, менять пришлось бы один файл.
2. **Полнотекстовый поиск** — `tsvector` + `GIN`-индекс вместо `ILIKE`,
   чтобы поиск понимал словоформы.
3. **Пагинация в интерфейсе** — API уже умеет `limit`/`offset`.
4. **Кэширование запросов** — SWR или React Query, когда экранов станет
   заметно больше.
5. **Уведомления в реальном времени** — Server-Sent Events как более
   простая альтернатива вебсокетам.
6. **Модульные тесты слоя данных** — в дополнение к сквозным.

## 10. Быстрые ответы на вероятные вопросы

**Почему Next.js, а не React + отдельный бэкенд?**
Один проект вместо двух: общие типы, один деплой, нет настройки CORS.
Для объёма этого ТЗ разделение дало бы только накладные расходы.

**Почему Postgres, а не MongoDB?**
Данные реляционные: пользователи, посты, лайки и подписки связаны.
Ограничение «один лайк на пользователя» в SQL — одна строка схемы,
в документной базе — ручная проверка с риском гонок.

**Почему Drizzle, а не Prisma?**
Prisma скачивает бинарные движки при установке; в закрытой сети проект
становится неустанавливаемым. Drizzle — чистый TypeScript. Плюс его
запросы ближе к SQL, поэтому видно, что именно уйдёт в базу.

**Где гарантия, что ключ OpenAI не утечёт?**
Три механизма: отсутствие префикса `NEXT_PUBLIC_`, директива `server-only`,
роняющая сборку при неправильном импорте, и проверяемый `grep` по бандлу.

**Что будет, если два человека лайкнут одновременно?**
Ничего страшного: составной первичный ключ в таблице `likes` не даст
вставить дубликат. Счётчик пересчитывается запросом `count(*)`, а не
хранится отдельным полем, поэтому рассинхрона не будет.

**Почему лента грузится на клиенте, а не приходит готовым HTML?**
ТЗ уровня 2 требует интеграцию собственного API. Явная граница
«браузер → API → база» делает архитектуру очевидной и переиспользуемой.
Плата — скелетоны при первой загрузке; для персонализированной ленты,
закрытой от поисковиков, это приемлемо.

**Что самое слабое в проекте?**
Отсутствие настоящей аутентификации и поиск по подстроке вместо
полнотекстового. Оба места названы в README и оба локализованы в одном
файле каждое.
